결제 승인 요청을 보냈는데 타임아웃이 났다. 결제는 된 걸까? 호출한 쪽은 알 수 없다. 응답을 못 받았을 뿐 PG는 승인을 끝냈을 수도 있다. 이럴 때 같은 요청을 그냥 다시 보내면 두 번 결제될 수 있고, 안 보내면 결제가 안 된 채로 끝날 수 있다. 같은 요청을 여러 번 보내도 한 번 보낸 것과 효과가 같은 성질을 멱등성이라고 한다. 결제 승인처럼 원래 멱등하지 않은 POST 요청을 멱등하게 만들 때 흔히 쓰는 방법이 멱등 키다.

## 1. 인용글 정리

### 큐는 같은 결제를 두 번 실행한다

> bugfix666, [Your Laravel Queue Will Run the Same Payment Twice. Build for It.](https://medium.com/@bugfix666/your-laravel-queue-will-run-the-same-payment-twice-build-for-it-6008bd6e7d46), Medium, 2026-10-31
>
> bugfix666, [Your Laravel Queue Is Not a Payment System](https://medium.com/@bugfix666/your-laravel-queue-is-not-a-payment-system-e5ae7bfb8b67), Medium, 2026-11-09

첫 글은 카드가 두 번 결제됐다는 고객 문의로 시작한다. DB에는 결제가 한 건이고 상태도 완료인데, PG에는 승인이 두 건 있다. 글이 드는 원인은 특별하지 않다. 워커가 PG에 승인을 요청했고 PG는 승인을 끝냈는데, 워커가 그 결과를 DB에 쓰기 전에 죽는 경우다. 메모리가 모자랐을 수도, 배포 중에 컨테이너가 재시작됐을 수도 있다. 라라벨은 작업이 끝났다는 확인을 받지 못했으니 작업은 다시 시도할 수 있는 상태가 되고, 다른 워커가 같은 코드를 돌려 승인을 한 번 더 받는다. 글쓴이 말로는 큐도 PG도 제 할 일을 했다. 두 시스템 사이에서 벌어지는 일에 애플리케이션이 대비하지 않았을 뿐이다.

그렇다고 재시도를 끄자는 건 아니다. 끄면 오히려 더 불안정해진다. 작업을 여러 번 실행해도 안전하게 만드는 게 답이고, 그게 멱등성이라고 말한다. 두 글이 권하는 방법은 이렇다.

- 결제 버튼을 막아 두면 화면에서는 도움이 되지만, 중복 결제가 안 난다는 보장은 못 된다. 요청에 멱등 키를 붙이고, 키는 결제와 함께 저장하되 같은 계정 안에서 키가 겹치지 않게 유니크 제약을 건다. 같은 키로 내용이 다른 요청(100달러가 1,000달러로 바뀐 식)이 오면 첫 결과를 조용히 돌려주지 말고 거절한다. 그러려면 첫 요청의 지문(fingerprint)도 같이 저장해 둬야 한다.
- PG가 멱등 키를 지원하면 결제에 딸린 키를 보내고, 재시도해도 바꾸지 않는다. 키는 결제 기록을 처음 남길 때 한 번 만들어 DB에 저장한다. 작업의 `handle()` 안에서 만들면 시도할 때마다 키가 바뀌어 PG는 매번 새 결제로 본다. 키를 얼마나 보관하는지, 같은 키에 다른 파라미터가 오면 어떻게 하는지는 PG마다 다르니 쓰는 PG의 문서를 직접 확인해야 한다. 멱등 키를 지원하지 않는 PG라면 주문 번호처럼 원래 거래를 찾을 수 있는 값으로 대사(reconciliation)한다.
- `exists()`로 확인한 뒤 `create()`를 부르는 코드에서는 두 워커가 동시에 확인을 통과할 수 있다. 중복은 DB 유니크 제약으로 막고, 위반이 나면 기존 행을 읽어 온다.
- 결제 API를 기다리는 동안 DB 트랜잭션을 열어 두지 않는다. 짧은 트랜잭션으로 상태부터 기록하고, PG 호출은 트랜잭션 밖에서 하고, 결과는 다시 짧은 트랜잭션으로 저장한다.
- 타임아웃은 결제가 실패했다는 증거가 아니다. 응답을 못 받았다는 뜻일 뿐이다. 그래서 완료와 실패 말고 '모름(UNKNOWN)' 상태를 두고, 원래 멱등 키나 주문 번호로 PG에 물어 실제로 어떻게 됐는지 확인한 뒤 상태를 바꾼다. 다시 보내도 되는 건 이전 요청이 처리되지 않았다는 게 확실할 때, 또는 같은 키로 다시 보내도 안전하다고 PG가 보장할 때뿐이다.
- 워커 타임아웃이 120초인데 `retry_after`가 90초면, 원래 워커가 아직 실행 중인 작업을 다른 워커가 다시 가져갈 수 있다. `ShouldBeUnique`는 락이 잡혀 있는 동안 중복 디스패치를 막아 줄 뿐, PG 결제가 실행되지 않았다는 걸 보장하지도 DB 제약을 대신하지도 못한다. 글쓴이 표현을 빌리면 락은 조율 장치일 뿐이다. 주문 하나에 결제는 한 번뿐이라는 식의 비즈니스 불변식은 그 조율이 실패해도 지켜져야 한다.
- DB 저장과 디스패치는 트랜잭션 하나로 묶이지 않는다. 트랜잭션 안에서 디스패치하면 롤백돼도 작업은 이미 나가 있을 수 있고, 커밋한 뒤에 디스패치하면 그 사이에 프로세스가 죽었을 때 작업이 사라진다. `afterCommit()`도 커밋한 뒤에 디스패치해 줄 뿐이라 뒤쪽 경우는 막지 못한다. 그래서 중요한 흐름에는 트랜잭셔널 아웃박스(Transactional Outbox)를 권한다. 보낼 메시지를 업무 데이터와 같은 트랜잭션으로 DB에 적어 두고, 따로 꺼내 보내는 방식이다. 글쓴이가 만든 라라벨 패키지를 예로 들고, 아웃박스도 같은 메시지를 다시 보낼 수 있으니 받는 쪽도 멱등해야 한다고 덧붙인다.
- 테스트는 가장 까다로운 상황부터 짠다. 가짜 PG가 승인은 기록하고 응답 대신 타임아웃 예외를 던지게 한 뒤, 재시도가 같은 키로 가서 장부에 한 건만 남는지 본다. 동시성 테스트는 가능하면 실제 DB 엔진으로 한다. 글이 예로 든 PostgreSQL의 잠금과 유니크 제약이 기대대로 동작하는지는 SQLite 테스트로는 알 수 없다.

첫 글은 이 말로 끝난다. 큐는 작업을 두 번 돌리게 두고, 업무 처리는 한 번만 일어나게 하라(Let the queue run the job twice. Make sure your business operation only happens once).

### 결제 요청을 세 단계로 나눈다

> Jon Chew, Ninad Khisti, [Avoiding double payments in a distributed payments system](https://medium.com/airbnb-engineering/avoiding-double-payments-in-a-distributed-payments-system-2981f6b070bb), The Airbnb Tech Blog, 2019-04-16

에어비앤비가 만든 멱등성 라이브러리 Orpheus 이야기다. 인프라를 서비스 지향 구조(SOA)로 옮기면서 여러 결제 서비스가 함께 쓰려고 만들었다. 글은 응답이 중간에 사라지거나 클라이언트 쪽에서 타임아웃이 났을 때, 사용자가 예약 버튼을 두 번 눌렀을 때 어떻게 할지에서 시작한다. 멱등성을 따로 서비스로 빼지 않은 데도 이유가 있다. 서비스로 빼면 지연 시간이 늘고, 무엇보다 그 서비스도 원래 풀려던 문제를 똑같이 겪는다.

- 요청 하나를 Pre-RPC, RPC, Post-RPC 세 단계로 나눈다. Pre-RPC에서는 요청 내용을 DB에 기록한다. RPC에서는 네트워크로 외부 서비스를 부르는데, 재시도라면 거래 상태부터 조회하는 식이다. Post-RPC에서는 응답과 성공 여부, 재시도할 수 있는 오류인지를 기록한다.
- 규칙은 두 가지다. Pre-RPC와 Post-RPC에서는 네트워크 호출을 하지 않고, RPC 단계에서는 DB를 건드리지 않는다. 앞뒤 단계에 네트워크 호출을 섞으면 커넥션 풀이 금방 바닥나고 성능이 떨어질 수 있다는 걸 직접 겪고 나서 알았다고 한다. 그 때문에 Pre-RPC와 Post-RPC는 각각 DB 트랜잭션 하나로 감쌌다.
- 오류는 재시도 가능과 재시도 불가로 나눈다. 네트워크나 인프라 문제로 생긴 5xx는 대체로 재시도 가능으로 보고, 잘못된 입력이나 상태(환불 건 자체를 환불할 수는 없는 것처럼) 때문에 생긴 4xx 검증 오류는 재시도 불가로 본다. 재시도 가능한 오류를 불가로 잘못 분류하면 그 요청은 계속 실패로 남고, 반대로 잘못 분류하면 이중 결제가 날 수 있다. 직접 만든 공통 예외 클래스는 기본값을 재시도 불가로 두고, 일부만 재시도 가능으로 분류했다.
- 재시도할 때 요청 본문이 바뀌면 안 된다. 클라이언트는 새 요청마다 새 키를 쓰고 재시도에는 같은 키를 쓰며, 서비스를 부르기 전에 키를 DB에 저장해 둔다.
- 키는 요청 단위(UUID 같은 무작위 값)로 정할 수도, 대상 단위로 정할 수도 있다. 결제 1234의 환불을 한 번만 허용하려면 `payment-1234-refund`처럼 대상에서 정해지는 키를 쓴다.
- 같은 키로 동시에 들어온 요청은 멱등 키 행을 잠가(행 잠금) 하나만 진행되게 한다. 글은 이걸 임대(lease)라고 부른다. 임대에는 만료가 있고, 만료 시간은 RPC 타임아웃보다 길게 잡는 게 좋다.
- 성공이나 재시도 불가 오류처럼 결과가 정해진 요청은 응답을 저장해 두고, 같은 요청이 다시 오면 그걸 돌려준다. 테이블이 계속 커지니 오래된 행을 주기적으로 지우는 방법을 들면서도, 너무 일찍 지우면 그것대로 문제가 된다고 짚는다.
- 멱등 정보는 복제본이 아니라 마스터(쓰기 DB)에서만 읽고 쓴다. 복제가 몇 초 늦는 사이에 재시도가 오면 응답 기록을 못 찾고 결제를 한 번 더 할 수 있다. 에어비앤비는 MySQL을 썼다.

이 라이브러리를 도입한 뒤 결제 정합성 99.999%를 달성했고, 같은 기간 연간 결제량은 두 배가 됐다고 한다.

### 요청 식별자를 API 계약에 넣는다

> Malcolm Featonby, [Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/), Amazon Builders' Library

글이 예로 든 건 EC2 인스턴스가 최대 한 대만 떠 있어야 하는 상황이다. 인스턴스를 띄우라고 요청했는데 응답이 오지 않았다. 다시 보내면 두 대가 뜰 수 있고, 대사를 해 봐도 결과를 확실히 알 수 없을 때가 있다.

- 요청 파라미터의 해시로 중복을 짐작하는 방법이 늘 통하지는 않는다. 같은 설정의 인스턴스 두 대가 정말 필요할 때도 있으니, AWS는 호출하는 쪽이 고유한 요청 식별자(EC2에서는 `ClientToken`)를 보내게 한다.
- 식별자를 기록하는 일과 리소스를 바꾸는 일은 원자적으로 한 번에 일어나야 한다. 식별자만 기록되고 리소스는 안 만들어지거나, 리소스는 만들어졌는데 식별자는 안 남는 일을 막기 위해서다.
- 이미 받은 요청에 `ResourceAlreadyExists` 같은 '이미 있다' 오류를 돌려주면 서버 쪽 부작용은 없어도 호출한 쪽의 흐름이 바뀐다. 대신 첫 응답과 의미가 같은 응답을 돌려준다. AWS SDK와 CLI는 이 계약을 지원하는 API라면, 호출하는 쪽이 식별자를 주지 않았을 때 직접 만들어 붙이고 재시도할 때 같은 값을 다시 쓴다.
- 같은 식별자로 파라미터가 다른 요청이 오면 다른 의도로 보고 파라미터 불일치 검증 오류를 돌려준다. 이걸 가려내려고 첫 요청의 파라미터도 식별자와 같이 저장해 둔다.
- 기록을 영원히 들고 있을 수는 없다. EC2는 리소스가 살아 있는 기간에 일정 기간을 더한 만큼만 보관한다.

글은 이 방식이 잘 통했다고 하면서도, 이런 계약을 지키려면 비용이 들고 구현도 복잡해져 모든 경우에 맞지는 않다고 본다. 그리고 '최대 한 번'이라는 엄격한 계약이 필요한 곳에서는 이 방식이 잘 맞았다는 말로 맺는다.

### 표준 초안과 공식 문서에 적힌 규칙

| 항목 | 내용 | 출처 |
| --- | --- | --- |
| HTTP 메서드 | GET, HEAD, OPTIONS, TRACE는 안전한 메서드이고, 이들과 PUT, DELETE는 멱등하다. POST는 그렇지 않다 | [RFC 9110 9.2.1, 9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2) |
| 자동 재시도 | 클라이언트는 멱등하지 않은 메서드의 요청을 자동으로 다시 보내지 않는 게 좋다(SHOULD NOT). 메서드와 상관없이 요청이 실제로 멱등하다는 걸 알거나, 원래 요청이 반영되지 않았다는 걸 알아낼 방법이 있을 때만 예외다 | 같은 곳 |
| `Idempotency-Key` 헤더 | IETF 표준 초안(08판, 2026-10-22). 키가 필요한 API에 키가 없으면 400, 같은 키로 본문이 다르면 422, 첫 요청이 아직 처리 중이면 409로 답하라고 한다(SHOULD) | [IETF 초안 08판](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-08) |
| Stripe | 키는 최대 255자. API v1 기준으로, 실행이 시작된 첫 요청의 상태 코드와 본문을 저장해 두었다가 같은 키로 다시 오면 그대로 돌려준다(500 포함). 키는 24시간이 지나면 지워질 수 있고, 그 뒤에 같은 키로 보내면 새 요청으로 처리된다. 파라미터가 다르면 오류. API v2는 동작이 다르다 | [Stripe 문서](https://docs.stripe.com/api/idempotent_requests) |
| 토스페이먼츠 | 모든 POST API에 `Idempotency-Key`를 붙일 수 있다. 최대 300자, 처음 요청한 날부터 15일 유효. 첫 요청이 처리 중이면 409 `IDEMPOTENT_REQUEST_PROCESSING` | [토스페이먼츠 문서](https://docs.tosspayments.com/reference/using-api/authorization#%EB%A9%B1%EB%93%B1%ED%82%A4-%ED%97%A4%EB%8D%94) |
| 토스페이먼츠 웹훅 | 10초 안에 200으로 답해야 한다. 전송에 실패하면 최대 7회 다시 보낸다(1, 4, 16, 64, 256, 1024, 4096분 간격) | [토스페이먼츠 웹훅 문서](https://docs.tosspayments.com/guides/v2/webhook) |
| Stripe 웹훅 | 같은 이벤트를 두 번 이상 보낼 수 있고 순서도 보장하지 않는다. 처리한 이벤트 ID를 기록해 걸러 내되, 같은 변경이 서로 다른 이벤트 두 개로 오는 경우도 있어 그때는 대상 객체의 ID와 이벤트 종류로 구분하라고 한다 | [Stripe 웹훅 문서](https://docs.stripe.com/webhooks#handle-duplicate-events) |
| Amazon SQS 표준 큐 | 최소 한 번 전달. 같은 메시지를 여러 번 처리해도 문제가 없게 만들라고 한다 | [SQS 문서](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html) |

토스페이먼츠 문서에는 멱등 키를 붙인 요청에 오류가 돌아왔을 때 키만 바꿔 같은 요청을 다시 보내면 위험하다고 적혀 있다. 오류 원인을 토스페이먼츠에 확인한 다음 다시 보내라고 한다.

라라벨 문서와 소스에서 알아 둘 것들이다.

1. `retry_after`는 처리 중인 작업을 몇 초 뒤에 다시 시도할지 정하는 값이다(새 프로젝트 설정에서 database와 redis 연결은 90초). `queue:work --timeout`의 기본은 60초다. 문서는 `--timeout`을 `retry_after`보다 몇 초 이상 짧게 두라고 경고한다. `--timeout`이 더 길면 작업이 두 번 처리될 수 있다([Laravel 13 문서: Job Expirations and Timeouts](https://laravel.com/docs/13.x/queues#job-expirations-and-timeouts)). SQS 큐에는 `retry_after`가 없고 SQS의 기본 표시 제한 시간(visibility timeout)을 따른다.
2. `ShouldBeUnique` 작업은 디스패치할 때 `uniqueId`로 락을 잡고, 락이 이미 있으면 디스패치하지 않는다. 락은 작업이 끝나거나 재시도 횟수를 다 쓰고 실패하면 풀린다([Laravel 13 문서: Unique Job Locks](https://laravel.com/docs/13.x/queues#unique-job-locks)).
3. `WithoutOverlapping` 미들웨어는 같은 키를 쓰는 작업이 겹치면(기본값은 같은 클래스끼리만) 뒤의 작업을 큐로 돌려보낸다. 돌려보낼 때도 시도 횟수가 올라가서, 한 번만 시도하는 기본 설정에서는 겹친 작업이 다시 실행될 기회가 없다([Laravel 13 문서: Preventing Job Overlaps](https://laravel.com/docs/13.x/queues#preventing-job-overlaps)).
4. `Cache::lock`에는 만료 시간을 줄 수 있다. 오래 걸리는 작업에는 락을 짧게 잡고 `refresh()`로 늘려 가는 방법도 문서에 있다([Laravel 13 문서: Refreshing Locks](https://laravel.com/docs/13.x/cache#refreshing-locks)).
5. `firstOrCreate`는 먼저 조회하고, 없으면 `createOrFirst`를 부른다. `createOrFirst`는 INSERT하다가 유니크 제약 위반이 나면 쓰기 연결로 같은 조건을 다시 조회한다([Eloquent Builder 소스](https://github.com/laravel/framework/blob/v13.43.0/src/Illuminate/Database/Eloquent/Builder.php#L753-L778)). 그러니 동시에 불려도 한 행만 남으려면 유니크 제약이 있어야 한다.

### 문서대로인지 직접 돌려 봤다

환경은 Docker `php:8.3-cli`(PHP 8.3.36), MySQL 8.4.13, 라라벨 13.43.0 새 프로젝트다. 캐시와 큐는 새 프로젝트 기본값인 `database` 드라이버를 그대로 써서 둘 다 MySQL에 있다.

PG는 PHP 파일 하나(`pg.php`)로 흉내 냈다. 승인 요청을 받으면 정해진 시간만큼 처리한 뒤 승인 한 건을 테이블에 남긴다. `Idempotency-Key` 헤더가 오면 처리하기 전에 키부터 저장하고, 같은 키가 다시 오면 본문이 다를 때는 422, 첫 요청이 처리 중일 때는 409, 끝났으면 저장해 둔 첫 응답을 돌려준다. 409와 422는 앞의 IETF 초안을, 첫 응답을 그대로 돌려주는 건 Stripe(API v1)를 따랐다.

#### 타임아웃 난 결제 요청을 다시 보내면

승인에 2초 걸리는 PG를 [1편](../resilience/timeout-retry-deadline.mdx)의 실험 C와 같은 `timeout(1)->retry(3, 200)`으로 불렀다.

|  | 보낸 방식 | 걸린 시간 | 받은 결과 | PG 승인(건) |
| --- | --- | --- | --- | --- |
| A | 멱등 키 없이 | 3.52초 | ConnectionException | 3 |
| B | `Idempotency-Key` 헤더를 붙여서 | 1.52초 | 409 | 1 |
| C | B가 끝나고 2초 뒤, 같은 키로 한 번 더 | 0.03초 | 200, B에서 승인된 건의 번호 | 1(그대로) |
| D | 같은 키로 금액만 바꿔서 | 0.03초 | 422 | 1(그대로) |

A는 클라이언트 쪽에서 보면 세 번 다 실패했는데, PG에는 승인이 세 건 남았다. 타임아웃은 '안 됐다'가 아니라 '모른다'는 뜻이다.

B는 두 번째와 세 번째 시도가 같은 키로 갔고, PG가 409(처리 중)로 답해서 승인은 한 건이었다. 라라벨 `retry()`는 조건을 안 주면 409 같은 4xx도 다시 보내는데, 세 번을 다 쓸 때까지 첫 요청이 처리 중이어서 결국 409를 받았다. 클라이언트는 여전히 결과를 모르지만, 같은 키로 다시 물으면 C처럼 첫 승인 결과를 받는다. 키를 재사용하면서 내용을 바꾼 D는 거절됐다.

#### 같은 주문에 결제 요청이 두 번 오면

결제 버튼을 두 번 누른 상황이다. 같은 주문으로 결제를 처리하는 프로세스 두 개를 0.1초 간격으로 띄웠다. FPM 워커 두 개가 요청을 하나씩 맡은 것과 비슷하다. PG 승인은 2초 걸린다.

|  | 처리 방식 | PG 승인(건) | 결제 행 | 두 번째 요청 |
| --- | --- | --- | --- | --- |
| E | 결제됐는지 확인 → PG 호출 → 저장 | 2 | 2 | "결제 완료" |
| F | E와 같고, `order_id`에 유니크 제약 | 2 | 1 | PG 승인 뒤 저장하다 `UniqueConstraintViolationException` |
| G | `pending`으로 먼저 저장 → PG 호출 → 결과 저장 | 1 | 1 | 0.01초 만에 "이미 처리 중" |
| H | E를 `Cache::lock('pay:주문번호', 10)->block(5)`로 감쌈 | 1 | 1 | 락을 기다렸다가 "이미 결제됨"(2.08초) |
| I | H에서 락 만료만 1초로 | 2 | 2 | 락을 잡고 "결제 완료" |

눈여겨볼 줄은 F다. 유니크 제약이 있어도 PG를 먼저 부르면 중복 승인은 막지 못한다. 제약은 승인이 이미 두 번 난 뒤에 두 번째 저장만 막았고, 그 요청은 예외로 끝났다. 사용자는 오류 화면을 봤겠지만 돈은 두 번 나간 상태다. G는 같은 제약을 두고 순서만 바꿨다. 결제 기록을 먼저 남겨 자리를 잡으니 두 번째 요청은 유니크 제약에 걸려 PG까지 가지 않았다. 에어비앤비 글의 Pre-RPC 단계를 넣은 셈이다.

H의 락도 중복 승인을 막았지만, 만료 시간에 기댄다. 만료를 PG 응답 시간보다 짧게 잡은 I에서는 첫 요청이 아직 PG를 기다리는 동안 락이 풀렸고, 두 번째 요청이 락을 잡아 승인을 한 번 더 받았다. 두 번째 요청이 락을 잡기까지 걸린 시간은 돌릴 때마다 달랐다(세 번 중 두 번은 0.5초쯤, 한 번은 거의 바로). database 캐시 드라이버는 락 만료 시각을 초 단위로 저장해서([DatabaseLock 소스](https://github.com/laravel/framework/blob/v13.43.0/src/Illuminate/Cache/DatabaseLock.php#L133-L140)), 1초짜리 락은 잡은 시점에 따라 1초가 되기 전에 풀린다.

마틴 클레프만이 분산 락 글에서 짚은 문제와 같은 모양이다. 클레프만은 락을 쓰는 이유를 효율(같은 일을 두 번 하지 않으려고)과 정확성(여러 프로세스가 같은 데이터를 건드려 상태가 깨지지 않게 하려고)으로 나눈다. 만료가 없으면 죽은 프로세스가 락을 영영 쥐고 있으니 만료는 필요하다. 그런데 락을 쥔 프로세스가 멈추거나 요청이 늦어져 만료를 넘기면, 락이 풀린 줄 모르고 안전하지 않은 변경을 할 수 있다. 그래서 정확성이 걸린 곳이라면 락만 믿지 말고 저장하는 쪽에서 한 번 더 막으라고 한다. 그 글이 내놓은 방법은 펜싱 토큰이다. 락을 잡을 때마다 커지는 번호를 받아 쓰기 요청에 붙이고, 저장하는 쪽이 이미 처리한 번호보다 작은 번호의 쓰기를 거절하게 하는 방식이다([How to do distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)).

#### 큐 작업이 두 번 실행되는 경우

PG 승인에 5초 걸리는 작업을 큐에 넣고 워커 두 개로 처리했다. 워커는 모두 `--timeout=30`이다. J부터 N까지는 `retry_after`를 일부러 작업 시간보다 짧은 3초로 뒀다.

|  | 설정 | 작업 시작 횟수 | PG 승인(건) | `failed_jobs`(행) |
| --- | --- | --- | --- | --- |
| J | `retry_after` 3초, `--tries=3` | 2 | 2 | 0 |
| K | J에 `ShouldBeUnique` | 2 | 2 | 0 |
| L | J에 `WithoutOverlapping` | 1 | 1 | 1 |
| M | J에 멱등 키(디스패치 전에 만들어 저장) | 3 | 1 | 0 |
| N | `retry_after` 3초, `--tries=1` | 1 | 1 | 1 |
| O | `retry_after` 90초(기본값), `--tries=3` | 1 | 1 | 0 |

J는 첫 워커가 작업을 시작하고 3.02초 뒤에 두 번째 워커가 같은 작업을 가져가 다시 실행했다. 첫 실행이 끝나기 전이라 PG 승인이 두 건이 됐다. 문서가 경고한 그대로다. `ShouldBeUnique`를 붙인 K도 결과가 같았다. 이 락은 디스패치할 때 잡는 것이라, 큐에 이미 들어간 작업을 다른 워커가 다시 가져가는 건 막지 않는다.

L의 `WithoutOverlapping`은 두 번째 실행을 막았다. 그 대신 두 번째 워커가 락을 못 잡고 작업을 큐로 돌려보내기를 되풀이하다 시도 횟수를 다 써서, 작업이 `failed_jobs`에 실패로 남았다. 실제로는 승인까지 끝난 작업이다. `--tries=1`인 N은 두 번째 워커가 아예 실행하지 않고 바로 실패로 기록했다. 둘 다 실패 기록과 실제 결제 결과가 어긋난 경우다.

M은 멱등 키를 디스패치하기 전에 만들어 결제 기록에 저장해 두고, 작업은 그 키를 꺼내 PG에 보냈다. 두 번째 시도는 PG에서 409를 받아 3초 뒤로 미뤘고(`release(3)`), 세 번째 시도는 PG가 저장해 둔 첫 응답을 받았다. 작업은 세 번 시작했지만 승인은 한 건이다. 다만 세 번째 시도가 첫 응답을 받은 건 그사이 PG 처리가 끝나서다. 409로 미뤄도 다시 꺼낼 때마다 시도 횟수가 오르니, PG가 더 오래 걸렸다면 `--tries=3`을 다 쓰고 L처럼 실패로 남았을 것이다. O는 `retry_after`를 기본값으로 돌려놓은 경우로, 다른 워커가 작업을 다시 가져가지 않아 한 번만 실행됐다.

#### firstOrCreate를 동시에 부르면

웹훅 이벤트를 기록할 때처럼 같은 이벤트 ID로 `firstOrCreate`를 프로세스 20개에서 같은 시각에 불렀다.

|  | 테이블 | 결과 | 남은 행 |
| --- | --- | --- | --- |
| P | `event_id`에 유니크 제약 없음 | created 11, found 9 | 11 |
| Q | `event_id`에 유니크 제약 | created 1, found 19 | 1 |

유니크 제약이 없으면 조회와 INSERT 사이에 끼어든 프로세스 수만큼 행이 생겼다. 몇 행이 생기는지는 돌릴 때마다 달랐다(세 번 돌려 6행, 3행, 11행). 제약이 있을 때는 예외 하나 없이 한 행만 남았다. 소스대로라면 INSERT하다 제약 위반이 난 프로세스에서는 `createOrFirst`가 다시 조회해 기존 행을 돌려준다.

```php title="pg.php"
<?php
// 가짜 PG. ?ms= 만큼 처리한 뒤 승인 한 건을 pg_charges에 남긴다.
// Idempotency-Key 헤더가 있으면 같은 키로 온 두 번째 요청부터는 승인하지 않는다.
ignore_user_abort(true); // 호출한 쪽이 끊어도 처리는 끝까지 한다
header('Content-Type: application/json');

$pdo = new PDO('mysql:host=mysql;dbname=lab', 'root', '', [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]);
$body = json_decode(file_get_contents('php://input'), true) ?? [];
$key = $_SERVER['HTTP_IDEMPOTENCY_KEY'] ?? null;
$fingerprint = hash('sha256', json_encode($body));

if ($key !== null) {
    try {
        // 처리하기 전에 키부터 잡는다. 같은 키가 있으면 유니크 제약에 걸린다.
        $pdo->prepare("INSERT INTO pg_idempotency (idem_key, fingerprint, status) VALUES (?, ?, 'processing')")
            ->execute([$key, $fingerprint]);
    } catch (PDOException $e) {
        if (($e->errorInfo[1] ?? 0) !== 1062) {
            throw $e;
        }
        $stmt = $pdo->prepare('SELECT * FROM pg_idempotency WHERE idem_key = ?');
        $stmt->execute([$key]);
        $row = $stmt->fetch(PDO::FETCH_ASSOC);

        if ($row['fingerprint'] !== $fingerprint) {
            http_response_code(422); // 같은 키, 다른 요청
```

## 2. 우리 프로젝트에 적용한다면

### 두 번 일어나면 안 되는 요청부터 고른다

쓰기 요청을 모아 놓고, 같은 요청이 두 번 오면 무슨 일이 생기는지 하나씩 적는다. 결제 승인과 취소, 환불, 포인트나 이용권 지급처럼 돈이나 권한이 움직이는 요청이 대상이다. 알림처럼 바깥으로 나가는 요청, PG 웹훅 수신, 큐 작업과 배치도 같이 본다. 같은 요청이 두 번 와도 결과가 같은 것(설정 값을 덮어쓰는 요청처럼)은 빼고, 두 번 일어나면 안 되는 것부터 손본다.

### 키는 업무에서 나온 값으로, 부르기 전에 저장한다

멱등 키는 재시도할 때 같은 값이 나와야 한다. 주문 하나에 결제가 한 번이라면 주문 번호에서, 결제 한 건의 환불이 한 번이라면 결제 번호에서 키를 만든다. 무작위 UUID를 쓴다면 처음 만들 때 저장해 두고 재시도에서는 저장한 값을 꺼내 쓴다. 시도할 때마다 새로 만들면 PG는 매번 새 결제로 본다. 반대로 카드 거절처럼 확실히 실패한 결제를 사용자가 다시 하는 건 새 시도라서 키도 새로 만든다. 주문 번호에 시도 회차를 붙이고, 회차는 앞 시도가 확실히 실패했을 때만 올린다.

PG가 멱등 키 헤더를 지원하면 이 키를 같이 보낸다. PG가 어떤 요청을 같은 요청으로 보는지는 문서로 확인한다. 토스페이먼츠는 멱등 키뿐 아니라 API 키, API 주소, HTTP 메서드까지 같아야 같은 요청으로 본다([토스페이먼츠 문서](https://docs.tosspayments.com/reference/using-api/authorization#%EB%A9%B1%EB%93%B1%ED%82%A4-%ED%97%A4%EB%8D%94)).

### 먼저 기록하고, 트랜잭션 밖에서 부르고, 결과를 기록한다

실험 G처럼 결제 기록부터 남기고 PG를 부른다. `createOrFirst`는 새로 만든 행이면 `wasRecentlyCreated`가 참이고, 이미 있던 행을 찾아 돌려줬으면 거짓이다. 이미 있던 행이 확실히 실패한 결제라면 조건을 건 UPDATE로 다음 회차를 잡는다. 두 요청이 동시에 와도 이 UPDATE는 하나만 성공한다.

```php title="결제 승인"
use Illuminate\Http\Client\ConnectionException;

// 1. 자리부터 잡는다. payments.order_id에는 유니크 제약이 있다(주문 하나에 결제 행 하나).
$payment = Payment::createOrFirst(['order_id' => $order->id], [
    'amount' => $order->amount,
    'status' => 'pending',
    'attempt' => 1,
    'idempotency_key' => "order-{$order->id}-1",
]);

if (! $payment->wasRecentlyCreated) {
    // 확실히 실패한 결제만 다음 회차로 다시 잡는다.
    $next = $payment->attempt + 1;
    $claimed = Payment::whereKey($payment->id)
        ->where('status', 'failed')
        ->where('attempt', $payment->attempt)
        ->update([
            'status' => 'pending',
            'attempt' => $next,
            'idempotency_key' => "order-{$order->id}-{$next}",
        ]);

    // 0이면 처리 중이거나 끝났거나 결과를 모르는 결제다. PG를 다시 부르지 않는다.
    if ($claimed === 0) {
        return $payment;
    }
    $payment->refresh();
}

// 2. DB 트랜잭션 밖에서 PG를 부른다. 다시 보낼 때도 같은 키를 쓴다.
try {
    $response = Http::timeout(5)
        ->withHeaders(['Idempotency-Key' => $payment->idempotency_key])
        ->post($approveUrl, ['order_id' => $order->id, 'amount' => $order->amount]);

    $status = match (true) {
        $response->successful() => 'paid',
        // PG 문서에 확정 실패로 적힌 코드(카드 거절 같은)만 failed로 둔다
        in_array($response->json('code'), $declineCodes, true) => 'failed',
        default => 'unknown', // 그 밖의 4xx, 5xx, 409는 결과를 모른다
    };
} catch (ConnectionException) {
    $status = 'unknown'; // 실패가 아니라 모름
}

// 3. 결과를 기록한다. 웹훅이나 대사가 먼저 확정했으면 덮어쓰지 않는다.
Payment::whereKey($payment->id)
    ->whereIn('status', ['pending', 'unknown'])
    ->update(['status' => $status]);
```

1에서 잡은 자리는 PG를 부르기 전에 커밋돼 있어야 다른 요청이 그 행을 보고 멈춘다. 그래서 이 코드는 바깥 트랜잭션 없이 부르고, 1과 3을 트랜잭션 하나로 묶어 그 안에서 PG를 부르지도 않는다. 그렇게 묶으면 PG를 기다리는 동안 커넥션과 잠금을 쥐고 있게 되고, 트랜잭션이 롤백되면 PG 승인은 남았는데 우리 기록만 사라진다.

`failed`는 PG 문서에 확정 실패로 적힌 코드(카드 거절 같은)에만 쓴다. 이 상태가 되면 사용자가 다시 결제할 수 있어서, 결과가 애매한 응답까지 `failed`로 적으면 이중 결제로 가는 길을 열어 주는 셈이다. 확정 실패 코드가 아닌 4xx(429, 409 같은)는 `unknown`에 두고 조회로 확정한다.

`unknown`이거나 `pending`에 오래 머문 결제는 스케줄러로 모아 PG 결제 조회 API로 상태를 확정한다. 승인돼 있으면 `paid`로, 거래가 없다고 확인되면 `failed`로 바꿔 다음 회차를 받을 수 있게 한다. 몇 번을 물어도 확정되지 않으면 사람이 보게 넘긴다. 에어비앤비 글은 이렇게 서버가 크론 작업 같은 것으로 정합성을 확인하는 방식을 비동기 복구(asynchronous repair)라고 부른다.

### 마지막 방어선은 유니크 제약이다

락은 만료 시간에, `ShouldBeUnique`는 큐 설정에, 버튼 막기는 화면에 기댄다. 실험 I와 K처럼 그 전제가 하나만 어긋나도 그대로 뚫린다. 주문당 결제 행이나 웹훅 기록의 이벤트 키처럼 한 번만 있어야 하는 값에는 유니크 제약을 건다. 실험 P와 Q에서 봤듯이 `firstOrCreate`도 유니크 제약이 있어야 동시에 불려도 한 행만 남는다.

### 웹훅은 받은 것부터 기록하고 빨리 답한다

토스페이먼츠는 10초 안에 200으로 답하라고 하고, 전송이 실패하면 최대 7회까지 다시 보낸다([토스페이먼츠 웹훅 문서](https://docs.tosspayments.com/guides/v2/webhook)). 처리가 길어져 제때 답하지 못하면 이미 처리한 웹훅을 다시 받을 수 있다는 뜻이다. 받은 이벤트를 유니크 제약이 걸린 테이블에 먼저 저장하고, 처리는 큐로 넘긴 뒤 바로 답한다.

```php title="웹훅 받기"
// webhook_events.event_key에는 유니크 제약이 있다
$event = WebhookEvent::createOrFirst(
    ['event_key' => $eventKey],
    ['payload' => $request->getContent(), 'status' => 'received'],
);

// 처음 온 이벤트든, 저장만 되고 처리가 안 끝난 이벤트든 큐에 넣는다.
// 작업 쪽도 같은 이벤트를 두 번 받아도 괜찮게 짠다.
if ($event->status === 'received') {
    HandlePaymentWebhook::dispatch($event->id);
}

return response('OK', 200); // 처음 온 것이든 중복이든 200
```

`wasRecentlyCreated`만 보고 디스패치하면 안 되는 이유는 저장과 디스패치가 하나로 묶이지 않아서다. 저장한 뒤 디스패치 전에 프로세스가 죽으면, PG가 다시 보내도 이미 있는 행이라 디스패치 없이 200만 나가고 그 이벤트는 영영 처리되지 않는다. 그래서 처리 상태를 같이 저장해 두고, 처리가 안 끝난 이벤트면 다시 넣는다. PG가 더는 보내지 않는 경우에 대비해 `received`로 오래 남은 이벤트는 스케줄러가 다시 넣게 해 둔다. 같은 이벤트가 두 번 들어갈 수 있으니 작업 쪽은 상태를 확인하고 한 번만 처리하게 짠다.

`$eventKey`에는 이벤트 ID가 있으면 그걸 쓴다. 다만 Stripe 문서에는 같은 변경이 ID가 다른 이벤트 두 개로 올 수 있다고 적혀 있다. 그렇다고 결제와 상태만 묶어 키를 만들면, 같은 결제에서 같은 상태가 여러 번 나올 때(부분 취소를 여러 번 하는 경우처럼) 두 번째 웹훅이 중복으로 걸러진다. 거래마다 달라지는 값이 있으면 그걸 키에 넣고, 마땅한 값이 없으면 웹훅은 'PG에 조회해 보라'는 신호로만 쓰고 상태는 조회 결과로 맞춘다.

웹훅 순서도 믿지 않는 게 좋다. Stripe는 이벤트 순서를 보장하지 않는다고 문서에 적어 두었다([Stripe 웹훅 문서](https://docs.stripe.com/webhooks#event-ordering)). 그러니 이미 취소된 결제를 승인으로 되돌리는 식의 변경은 받지 않는다. 웹훅이 정말 PG에서 왔는지 확인하는 일은 저장보다 먼저 한다.

### 큐 작업은 두 번 돈다고 보고 짠다

`retry_after`는 가장 오래 걸리는 작업보다 길게 잡고, `--timeout`은 `retry_after`보다 몇 초 이상 짧게 둔다. 바깥 호출이 있는 작업이라면 [1편](../resilience/timeout-retry-deadline.mdx)에서 정한 타임아웃과 재시도 대기 시간을 모두 더한 값보다 `--timeout`이 길어야 한다. SQS처럼 `retry_after`가 없는 큐는 표시 제한 시간이 같은 역할을 한다.

설정을 맞춰도 워커가 죽거나 배포로 끊기면 작업은 다시 돈다. 그래서 작업 안에서 이미 끝난 일인지 쓰기 DB에서 먼저 보고, PG에는 디스패치 전에 저장해 둔 키를 보낸다. 409를 받으면 실패로 끝내지 말고 잠시 뒤에 다시 묻는다. 실험 M에서 봤듯이 409로 미뤄도 시도 횟수는 오르니, 재시도는 횟수 대신 시간(`RetryFor`)으로 제한한다. 그 시간을 다 써도 끝나지 않으면 `failed()`에서 결제를 '모름'으로 남겨 대사로 넘긴다.

```php title="ChargePayment.php"
namespace App\Jobs;

use App\Models\Payment;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;
use Illuminate\Queue\Attributes\Backoff;
use Illuminate\Queue\Attributes\RetryFor;
use Illuminate\Queue\Attributes\Timeout;
use Illuminate\Support\Facades\Http;
use Throwable;

#[RetryFor(minutes: 10)]  // 횟수 대신 시간으로 재시도를 제한한다
#[Backoff(5, 15, 30, 60)] // 연결 오류 뒤에 바로 다시 보내지 않는다
#[Timeout(30)]            // retry_after(기본 90초)보다 짧게
class ChargePayment implements ShouldQueue
{
    use Queueable;

    public function __construct(public int $paymentId) {}

    public function handle(): void
    {
        // '이미 처리했나'는 쓰기 DB에서 읽는다
        $payment = Payment::onWriteConnection()->findOrFail($this->paymentId);

        if ($payment->status !== 'pending') {
            return; // 이미 끝났거나 확인이 필요한 결제다
        }

        $response = Http::timeout(10)
            ->withHeaders(['Idempotency-Key' => $payment->idempotency_key])
            ->post(config('services.pg.approve_url'), [
                'order_id' => $payment->order_id,
                'amount' => $payment->amount,
            ]);

        if ($response->status() === 409) {
            $this->release(5); // 같은 키의 첫 요청이 아직 처리 중이다
            return;
        }

        $declineCodes = config('services.pg.decline_codes'); // PG 문서의 확정 실패 코드
        $status = match (true) {
            $response->successful() => 'paid',
            in_array($response->json('code'), $declineCodes, true) => 'failed',
            default => 'unknown',
        };

        Payment::whereKey($payment->id)
            ->whereIn('status', ['pending', 'unknown'])
            ->update(['status' => $status]);
    }

    // 재시도 시간을 다 써도 결과를 모르면 '실패'가 아니라 '모름'으로 남겨 대사로 넘긴다
    public function failed(?Throwable $exception): void
    {
        Payment::whereKey($this->paymentId)
            ->where('status', 'pending')
            ->update(['status' => 'unknown']);
    }
}
```

`failed_jobs`는 '안 된 결제' 목록이 아니다(실험 L, N). `queue:retry`로 다시 돌리기 전에 PG에서 상태부터 확인한다.

### '이미 처리했나'는 쓰기 DB에 묻는다

읽기 복제본을 같이 쓰고 있다면 멱등 키를 확인하는 조회는 쓰기 연결로 보낸다. 에어비앤비 글이 짚었듯이 복제가 몇 초 늦으면 처리한 기록을 못 보고 한 번 더 처리할 수 있다. 라라벨의 `sticky` 옵션은 같은 요청 안에서 쓰기를 한 뒤의 읽기만 쓰기 연결로 보내 주므로([Laravel 13 문서: The sticky Option](https://laravel.com/docs/13.x/database#the-sticky-option)), 다른 요청이나 워커가 확인할 때는 도움이 안 된다. 쿼리에 `useWritePdo()`를 붙이거나 모델에서 `onWriteConnection()`으로 시작하면 쓰기 연결을 쓴다([Query Builder 소스](https://github.com/laravel/framework/blob/v13.43.0/src/Illuminate/Database/Query/Builder.php#L4878-L4883), [Model 소스](https://github.com/laravel/framework/blob/v13.43.0/src/Illuminate/Database/Eloquent/Model.php#L866-L869)). `createOrFirst`도 유니크 제약 위반 뒤 다시 조회할 때 `useWritePdo()`를 쓴다.

### 테스트는 '처리됐는데 응답이 없는' 경우부터

가짜 PG가 승인은 남기고 응답 대신 타임아웃 예외를 던지게 해서, 재시도가 같은 키로 가고 승인이 한 건만 남는지 본다. 동시성 테스트는 운영과 같은 DB 엔진에서 돌린다. 위 실험도 SQLite가 아니라 MySQL에서 돌렸다.

## 3. 개인적인 견해

도구보다 순서가 먼저라고 본다. 실험 F와 G는 유니크 제약이 똑같았는데, PG를 언제 부르느냐 하나로 승인이 두 건과 한 건으로 갈렸다. 멱등 키 테이블이나 락을 고민하기 전에 먼저 기록하고, 트랜잭션 밖에서 부르고, 결과를 기록하는 순서부터 지키는 게 맞다고 생각한다.

락은 보조 장치로 두는 편이 낫다. 실험 I처럼 만료를 PG 응답 시간보다 짧게 잡으면 그대로 두 번 승인된다. 1편에서 봤듯이 바깥 호출은 생각보다 오래 걸릴 수 있어서, 만료를 '충분히 길게' 잡는다는 말부터 믿기 어렵다. 클레프만의 구분대로 같은 일을 두 번 하는 낭비를 줄이는 데는 락을 쓰고, 두 번 일어나면 안 되는 일은 유니크 제약으로 막겠다.

'모름' 상태를 하나 더 두는 게 처음엔 번거로워 보인다. 그래도 타임아웃을 '실패'로 적어 두면 결국 누군가 PG 관리자 화면과 DB를 손으로 맞춰 보게 된다. 상태 하나와 그걸 확인하는 스케줄러 하나를 두는 편이 그 수작업보다 싸다.

큐 실험에서 가장 위험해 보인 건 L과 N이다. 실패로 기록된 작업이 실제로는 승인까지 끝나 있었는데, 실패 목록을 보면 다시 돌리고 싶어지는 게 당연하다. 재처리하기 전에 PG에 상태를 묻는 단계까지 멱등 설계에 넣어야 한다고 생각한다.

우리 API가 `Idempotency-Key` 헤더를 받게 하는 건 그다음 일 같다. 웹과 앱이 키를 만들어 저장하고 재시도 때 다시 보내야 해서 클라이언트 쪽 일이 크다. 당장은 서버 안에서 주문 번호 같은 업무 키와 유니크 제약으로 중복을 막고, PG 호출에 키를 붙이는 데서 시작하겠다. 토스페이먼츠도 처리 중인 요청에 409를 쓰니, 나중에 헤더를 받게 되면 IETF 초안의 409, 422 규칙을 그대로 따르면 될 것 같다.
