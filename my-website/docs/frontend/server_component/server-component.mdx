### 서버 컴포넌트는 왜 나왔을까?

아래와 같은 React의 문제점들을 해결해보고자 서버 컴포넌트가 나왔다.

#### React의 기존 문제점 3가지

1. Bundle Size Trap

- 브라우저에 불필요한 javascript까지 전달하는 문제
- React는 브라우저가 컴포넌트를 실행해서 화면을 만드는 구조이다.<br/>
  여기서 문제는 컴포넌트가 실제로는 javascript 함수라는 것이다. <br/>
  아래와 같은 jsx는 JavaScript로 변환된다. 우리 눈으로 봤을 때 단순한 html만 반환하는 것처럼 보여도...!

  ```
   function Header() {
      return <header>안녕하세요</header>;
  }
  ```

2. Waterfall Problem

- 데이터를 순차적으로 요청하면서 페이지가 느려지는 문제
- waterfall: 앞선 데이터 요청이 끝나야 다음 데이터 요청을 시작할 수 있는 현상 <br/>
- 예를 들어, 클래스 컴포넌트 렌더(useEffect로 클래스 조회 api 완료되어야 강사 컴포넌트) -> 강사 컴포넌트 렌더(강사 api 조회)
- loaders나 getServerSideProps로 미리 데이터(클래스, 강사 데이터)를 받아와서 자식 컴포넌트에 넣어주는 식으로 해결할 수도 있지만 그러면 컴포넌트의 캡슐화가 깨질 수 있다.

3. Hydration Tax

- 이미 HTML을 만들었는데도 브라우저에서 컴포넌트를 다시 실행해야 하는 문제
- SSR(Server Side Rendering)을 사용하면 서버가 먼저 HTML을 생성해준다. <br/>
  하지만 여기에는 React의 onClick이나 useState 상태 관리가 없어서 <br/>
  다시 React JavaScript를 실행해 기존 HTML과 컴포넌트 로직을 연결해야하는 데 이걸 Hydration이라고 한다.
  이걸 해야 버튼 클릭 이벤트 같은 상호작용이 가능해진다.
- 여기서 문제는 사용자와 상호작용 필요없는 컴포넌트까지 Hydration 한다는 것이다.

=> 그래서 서버 컴포넌트는 이런 문제를 해결하기 위해 나온, 기존의 클라이언트 컴포넌트와는 다른 두번째 컴포넌트이다.

### 서버 컴포넌트는 SSR 2.0이 아니다!

> But it cannot use useState, useEffect, or event handlers, because it never runs in the browser. It is not hydrated. It is not even sent to the browser as JavaScript.

- 서버 컴포넌트는 서버에서 실행된다.
- 브라우저에서 실행되지 않기 때문에 useState, useEffect, event handlers를 사용할 수 없다.
- 자바스크립트 형태로 브라우저에 전송되지도 않는다.

> This is not SSR. SSR renders your entire app on the server to produce HTML, then rehydrates it in the browser. RSC renders specific components on the server and never sends their code to the browser at all.

- SSR은 서버에서 전체 앱을 렌더링하여 HTML을 생성한 다음 브라우저에서 다시 로드한다.
- RSC는 서버에서 컴포넌트만 렌더링하고 해당 코드는 브라우저로 전혀 전송하지 않는다.

| 구분            | SSR(Server Side Rendering)      | RSC(React Server Component)         |
| --------------- | ------------------------------- | ----------------------------------- |
| 개념            | 렌더링 방식                     | 컴포넌트 종류                       |
| 주요 목적       | 서버에서 HTML 생성              | 서버와 클라이언트의 실행 역할 분리  |
| 서버 실행       | HTML 생성에 사용                | Server Component 실행               |
| 브라우저 JS     | 기존 SSR에서는 Hydration에 필요 | Server Component 자체의 JS는 불필요 |
| 함께 사용 가능? | 가능                            | 가능                                |

## 2. 우리 프로젝트에 적용한다면?

지금은 SSR과 Client Component로 구성되어있는데
이 구성에 서버 컴포넌트까지 넣어서 처리해볼 수 있을 거 같다.
(물론 그 전에 버전 업데이트가 필요하겠지만...)

저번에 우리 프로젝트 성능 확인 했을 때 결과가 썩 좋지 않았다.
서버 컴포넌트를 도입하면 브라우저에서 실행할 JavaScript를 줄일 수 있기 때문에
이런 부분에서 효과가 있지 않을까 기대해본다. (-> 이것은 추측이라 확인이 필요하다.)

서버 컴포넌트를 알아보면서 SSR에 대해서도 한번 더 생각하게 됐다.
이 프로젝트에 SSR을 처음 도입했던 가장 큰 이유가 SEO였기 때문에
서버에서 데이터를 미리 받아와서 처리하는 SSR의 특징을 잘 살려서 써보려는 고민을 하지 않고 사용했었다.
서버 컴포넌트를 도입하기 전까지 프로젝트에서 SSR을 어떻게 하면 더 잘 쓸 수 있을 지 고민해봐야겠다.

## 3. 마무리

서버 컴포넌트를 다른 프로젝트에서 사용해본 경험은 있는데 그 때도 모르고 쓴다고 생각했지만 진짜 모르고 썼던 거였다.

이것저것 공부하면서 연결해서 생각해 보는 게 재밌었다.
이걸하면 성능이 좀 좋아지려나 생각해보기도 하고 유익한 시간이었다!
이제 3개째라 연결해서 생각해볼 건 많이 없었지만...!

공부한 게 많으면 공부한 것들이 파바박 연결되어서 좀 더 재밌어지지 않을까 기대해본다. <br/>
공부하면서 이렇게 생각해보는 시간으로 자신의 견해를 쌓아나가는 거 같다!
