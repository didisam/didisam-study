며칠 전 저녁, 산타 개발팀의 Claude Code · Codex 토큰 사용량을 랭킹으로 보여 주는 [토큰 대시보드](https://didisam.github.io/token-dashboard/?period=week&tool=all&metric=total)를 만들었다. 서로 얼마나 쓰는지 보면 재밌겠고, 재밌으면 더 써 보게 되지 않을까 하는 가벼운 마음이었다.

그런데 숫자를 들여다볼수록 질문이 커졌다. 우리는 이 도구를 어떤 태도로 대하고 있을까. 사용량을 재는 게 맞기는 할까. 그리고 이 도구가 더 똑똑해지면, 개발자인 우리에게는 무엇이 남을까.

:::tip[세 줄 요약]
- **과거**: 프로그래밍의 역사는 위임의 역사다. 다만 지금까지 코드를 맡긴 도구는 같은 조건이면 같은 결과를 내도록 만들 수 있었고, AI는 출력 자체가 확률적이다. 초기의 의심은 거기서 왔다.
- **현재**: 위임의 단위가 한 줄에서 작업 하나로 커졌다. 데이터를 보면 토큰의 97.6%가 이미 보낸 컨텍스트를 다시 보내는 데서 나온다. 이제 코드를 짜는 것만큼 컨텍스트를 설계하는 일이 중요하다.
- **미래**: 사용량은 목표가 되는 순간 지표로서 힘을 잃는다. AI가 더 많은 일을 할수록 사람에게 남는 건 문제를 정의하고, 판단하고, 책임지는 일이다. 그 능력은 의식적으로 지키지 않으면 녹슨다.
:::

## 1. 과거: 우리는 늘 무언가에 위임해 왔다

### 위임의 사다리

AI가 처음 나왔을 때 많은 개발자가 불안해했다. "이걸 쓰면 내가 코드를 이해하지 못하게 되지 않을까?" 그런데 이 불안은 새로운 게 아니다.

프로그래밍의 역사는 위임의 역사다. 기계어를 직접 쓰던 사람들은 어셈블러에 위임했고, 어셈블리를 쓰던 사람들은 컴파일러에 위임했다. 메모리 관리는 가비지 컬렉터에, 쿼리 실행 계획은 DB 옵티마이저에, 화면 갱신은 React에 맡겼다. 단계마다 "이러다 진짜 원리를 모르는 개발자가 나온다"는 걱정이 있었고, 실제로 그런 개발자가 나왔고, 그래도 생산성은 계속 올라갔다.

조엘 스폴스키는 2002년에 이걸 ["새는 추상화의 법칙"](https://www.joelonsoftware.com/2002/11/11/the-law-of-leaky-abstractions/)으로 정리했다. 모든 추상화는 어딘가에서 샌다. 평소엔 아래층을 몰라도 되지만, 문제가 터지는 순간엔 결국 아래층을 알아야 한다. [큐 테이블에 왜 SKIP LOCKED를 붙였을까](../../backend/database/locking-reads.mdx) 글이 딱 그런 경우다. 라라벨의 `lock()` 한 줄 아래에는 InnoDB가 인덱스 레코드에 잠금을 거는 방식이 있었고, 그걸 모르면 워커를 늘려도 하나만 일한다.

### 그런데 AI는 출력 자체가 확률적이다

비결정적인 시스템이 AI가 처음은 아니다. 동시성 버그는 재현될 때도 있고 안 될 때도 있고, 랜덤 알고리즘이나 확률적 최적화도 오래전부터 있었다. 컴파일러도 타임스탬프나 의존성 버전에 따라 다른 바이너리를 내서, 같은 결과를 보장하려고 재현 가능한 빌드(reproducible build)라는 노력이 따로 있을 정도다.

다만 지금까지 **코드를 맡긴 도구**에는 공통점이 있었다. 비결정성을 줄이고 결과의 재현성을 확보하는 게 중요했고, 환경을 고정하면 같은 입력에 같은 출력이 나오도록 만들 수 있었다. 그래서 한 번 검증하면 계속 믿을 수 있었다. 우리가 컴파일러가 낸 어셈블리를 매번 읽지 않는 이유다.

AI는 다르다. 샘플링이 동작 방식의 일부라서, 같은 질문에 다른 답을 내는 게 결함이 아니라 원래 그렇다. 모델이 바뀌면 어제 맞던 답이 오늘은 틀리기도 한다. 없는 API를 아주 자신 있게 지어내기도 한다. AI를 처음 접했을 때 우리가 느낀 불편함은 "기계가 코드를 짠다"는 것보다 이 쪽에 더 가까웠던 것 같다. 믿는 방법을 몰랐던 것이다.

그래서 초기의 태도는 대체로 이랬다.

- **자동완성 정도로만 쓴다.** 틀려도 바로 눈에 보이는 범위까지만 맡긴다.
- **결과를 전부 다시 확인한다.** 결국 문서를 다시 열어야 했으니, 빨라졌는지 애매했다.
- **쓰는 걸 굳이 말하지 않는다.** AI가 짠 코드라고 하면 덜 고민한 것처럼 보일까 봐 조용히 썼다.

## 2. 현재: 위임의 단위가 바뀌었다

### 한 줄에서 작업 하나로

지금은 하루 대부분을 AI 코딩 에이전트와 같이 보낸다. 바뀐 건 사용 빈도만이 아니다. **한 번에 맡기는 단위**가 달라졌다.

| 시기 | 맡기는 단위 | 사람이 하는 일 |
|---|---|---|
| 자동완성 | 한 줄 | 거의 다 직접 짜고, 제안을 받아들이거나 버린다 |
| 채팅 | 함수 하나 | 질문하고, 복사해 붙이고, 고친다 |
| 에이전트 | 작업 하나 | 목표와 제약을 설명하고, 결과를 검증한다 |

에이전트 단계에서 개발자의 일은 **쓰는 사람**에서 **설명하고 판정하는 사람**으로 옮겨 간다. 코드를 직접 치는 시간은 줄고, 무엇을 만들지 정의하는 시간과 만들어진 걸 의심하는 시간이 늘어난다.

### 그런데 아무도 숫자를 몰랐다

이렇게 일하는 방식이 통째로 바뀌었는데, 팀 전체로 보면 아무것도 보이지 않았다. 다들 개인 구독이라 관리자 콘솔이 없다. 그래서 토큰 대시보드를 만들었다.

- 각자 PC의 CLI 로그(`~/.claude/projects`, `~/.codex/sessions`)를 1시간마다 읽어서, 날짜 × 도구 × 모델별 **토큰 합계만** Git 리포에 push한다. 프롬프트, 코드, 프로젝트 이름은 어디에도 남지 않는다.
- 서버도 DB도 없다. GitHub Actions가 매시 정각에 파일을 합쳐 GitHub Pages로 배포한다.
- 관리 화면보다는 게임 같은 화면을 골랐다. 시상대, 순위 변동, 불꽃 스트릭과 출력왕 같은 타이틀이 있다.

하룻밤 만에 만들 수 있었던 건 이것도 AI와 같이 만들었기 때문이다. 다만 화면은 금방 나왔는데, **숫자가 맞는지**를 확인하는 데 시간이 더 걸렸다. Claude Code는 응답 하나를 여러 줄로 기록해서 그대로 더하면 사용량이 몇 배로 부푼다. Codex는 입력 토큰에 캐시 적중분을 포함해서 Claude와 기준이 다르다. 오래된 로그는 자동으로 지워진다. 이런 건 AI가 알아서 잡아 주지 않았다. 내가 이상하다고 느끼고 물어봐야 잡혔다.

### 숫자 읽기 1: 곡선이 가파르다

2026년 11월 25일 기준, 다섯 명의 누적 사용량은 약 177억 토큰이다. 이 중 약 5억은 6월부터 10월 중순까지 띄엄띄엄 남아 있는 기록이고, 사용량이 본격적으로 잡히기 시작한 10월 19일 주부터 보면 이렇다.

| 주(월요일 시작) | 총 토큰 | 출력 토큰 |
|---|---|---|
| 10월 19일 | 2.8억 | 100만 |
| 10월 26일 | 6.7억 | 250만 |
| 11월 2일 | 11.8억 | 450만 |
| 11월 9일 | 30.6억 | 1,190만 |
| 11월 16일 | 45.9억 | 1,600만 |
| 11월 23일 (3일치) | 74.6억 | 2,330만 |

표의 숫자만 보면 한 달 사이에 주간 사용량이 스무 배 넘게 늘었고, 이번 주는 사흘 만에 지난주를 넘었다. 다만 이 배수를 그대로 믿기는 어렵다. Claude Code는 기본 설정에서 30일이 지난 로그를 지우기 때문에, 대시보드를 만들기 전 기간은 실제보다 작게 잡혔을 가능성이 크다. 정확히 몇 배인지는 대시보드가 쌓아 갈 앞으로의 데이터로 다시 봐야 한다. 그래도 곡선의 방향만큼은 분명하다. 우리는 지금 도구를 "써 보는" 단계를 지나 "기대는" 단계로 넘어가는 중이다.

### 숫자 읽기 2: 사용량의 대부분은 기존 컨텍스트에서 나온다

토큰을 종류별로 나누면 더 흥미롭다.

| 종류 | 토큰 비율 | 환산 비용 비율 |
|---|---|---|
| 캐시 읽기 | 97.6% | 60.5% |
| 입력(캐시 미적중) | 1.3% | 5.7% |
| 캐시 쓰기 | 0.7% | 13.9% |
| 출력 | 0.3% | 19.9% |

여기서 환산 비용은 실제로 낸 돈이 아니다. 우리는 정액 구독이라, 같은 토큰을 API로 썼다면 얼마였을지를 정가로 계산해 본 참고값이다.

AI가 실제로 써 낸 출력은 전체 토큰의 0.3%다. 나머지 대부분은 이미 한 번 보냈던 대화와 파일을 **다시 보내면서** 생긴 토큰이다.

오해하지 말아야 할 점이 있다. 토큰 비율은 시간 비율이 아니다. 프롬프트 캐시는 앞부분 컨텍스트의 연산 결과를 저장해 두고 재사용하는 기술이라, 캐시 적중분은 처음부터 다시 계산하지 않는다. 그래서 캐시 읽기 단가도 일반 입력보다 훨씬 싸다. "AI가 시간의 97%를 다시 읽는 데 쓴다"가 아니라 "집계된 전체 토큰의 97.6%가 기존 컨텍스트에서 나온다"가 정확한 말이다.

이렇게 되는 이유는 에이전트가 동작하는 방식에 있다. 모델 자체는 요청과 요청 사이에 대화 상태를 들고 있지 않는다. 그래서 클라이언트가 매 요청마다 지금까지의 대화, 읽은 파일, 도구 실행 결과를 다시 붙여 보낸다. Claude Code 기준으로 요청 한 번에 평균 23만 토큰이 실려 가고, 세션 하나에 요청이 평균 319번 오간다.

여기서 개발자라면 계산을 한 번 해 볼 만하다. 턴마다 컨텍스트가 k만큼 일정하게 늘고 중간에 요약·압축이 없다고 가정하면, n번째 요청은 약 n·k를 보낸다. 세션 전체로는 k·n(n+1)/2, 즉 **세션 길이의 제곱**에 비례한다. 이 가정에서는 같은 일을 긴 세션 하나로 하는 것이 짧은 세션 세 개로 나눠 하는 것보다 세 배쯤 많은 토큰을 쓴다. 실제로는 Claude Code가 컨텍스트가 차면 자동으로 압축하고, 세션마다 공통으로 실리는 시스템 프롬프트도 있어서 정확히 세 배는 아니다. 그래도 방향은 같다. 캐시 덕분에 단가는 싸지만, 환산 비용의 60%가 여전히 여기서 나온다.

비용만의 문제도 아니다. 컨텍스트가 길어질수록 모델은 앞쪽 내용을 흐리게 다루고, 오래전에 했던 잘못된 가정을 계속 끌고 간다. 결국 **AI에게 무엇을 보여 줄지 고르는 일**이 결과의 품질과 비용을 동시에 결정한다. 예전에 함수를 작게 나누고 의존성을 좁혔듯이, 이제는 컨텍스트를 작게 나누고 좁히는 게 실력이 된다.

### 숫자 읽기 3: 같은 팀, 다른 사용법

도구별로 나누면 사용 방식이 확연히 다르다.

| 도구 | 총 토큰 | 세션 수 |
|---|---|---|
| Claude Code | 87.5억 | 120 |
| Codex | 89.8억 | 588 |

총 토큰은 둘이 거의 반반인데 쓰이는 모양은 정반대다. Claude Code는 긴 세션이 적게 있고, Codex는 짧은 세션이 다섯 배쯤 많다.

요청 단위로 더 쪼개 보고 싶었지만 여기서 멈췄다. Claude Code는 API 호출 하나가 로그 한 건이라 요청 수를 셀 수 있다. 반면 Codex는 누적 토큰 카운터만 남기고, 그 카운터가 API 호출마다 찍히는지 사용자 턴마다 찍히는지 로그만으로는 확신할 수 없었다.

실제로 일별 데이터를 보면 의심할 만한 값이 있다. Codex의 요청당 컨텍스트는 중앙값이 12만 토큰 정도로 평범한데, 요청 한 번에 1,000만 토큰이 넘게 잡힌 날도 있었다. API 호출 한 번으로는 나올 수 없는 크기다. 이런 값이 평균을 끌어올려서, 처음 계산했을 때는 Codex의 요청당 평균이 39만 토큰으로 나왔다. 기준이 다른 두 숫자를 나란히 놓으면 비교가 아니라 착시가 된다. 대시보드도 아직 이 부분은 정확하지 않을 수 있다.

세션 통계만으로 각 세션에서 무슨 일을 했는지까지 알 수는 없다. 대화 내용을 모으지 않기로 했으니 당연하다. 도구마다 세션을 나누는 기준이 달라서 생긴 차이일 수도 있다. 다만 같은 팀이 같은 기간에 쓴 두 도구가 이 정도로 다른 모양을 보인다는 건, "AI를 쓴다"는 한마디 안에 꽤 다른 작업 방식이 섞여 있다는 뜻이기도 하다.

## 3. 측정의 역설: 재는 순간 달라진다

랭킹을 만들어 놓고 가장 오래 붙잡은 질문은 이것이다. **많이 쓰는 게 잘 쓰는 걸까?**

경제학에는 [굿하트의 법칙](https://en.wikipedia.org/wiki/Goodhart%27s_law)이 있다. 어떤 지표가 목표가 되면, 그 지표는 더 이상 좋은 지표가 아니다. 소프트웨어 업계는 이걸 이미 한 번 겪었다. 코드 줄 수로 생산성을 재던 시절, 사람들은 코드를 길게 짰다. 토큰 사용량도 똑같다. 랭킹 1위를 목표로 삼으면, 가장 쉬운 방법은 컨텍스트를 정리하지 않고 긴 세션을 계속 돌리는 것이다. 앞에서 본 것처럼 그건 비싸고 품질도 떨어지는, 정확히 **나쁜 사용법**이다.

토큰은 입력이지 결과가 아니다. 대시보드는 AI에 얼마나 기댔는지는 보여 주지만, 그걸로 무엇을 만들었는지는 보여 주지 못한다.

그런데도 대시보드를 내리지 않은 이유가 있다. 지금 우리에게 필요한 건 효율보다 **노출**이라고 생각해서다. 어떤 일을 맡겨도 되는지, 어디서 사람이 붙잡아야 하는지는 써 본 만큼만 알 수 있다. 그래서 랭킹 기준을 하나로 두지 않고 총 토큰, 출력 토큰, 환산 비용, 세션 수, 활동일 중에서 고를 수 있게 했다. 기준을 바꾸면 순위가 꽤 달라진다. 하나의 숫자로 사람을 줄 세우지 않겠다는 장치이기도 하다.

그래서 분명히 적어 둔다. **이 대시보드의 숫자는 개인의 생산성이나 개발 역량을 평가하는 지표가 아니다.** 많이 쓰는 사람도, 적게 쓰는 사람도 각자의 방식이 있다. 우리가 보고 싶은 건 개인의 순위가 아니라, 팀 전체가 일하는 방식이 어떻게 바뀌고 있는가다.

언젠가는 이 대시보드가 역할을 다하는 날이 올 것이다. 모두가 충분히 써 봤고, 이제 얼마나 쓰는지보다 어떻게 쓰는지가 궁금해지는 날이다.

## 4. 미래: 사람에게 남는 것

### 자동화의 아이러니

1983년, 리산 베인브리지는 [「자동화의 아이러니(Ironies of Automation)」](https://doi.org/10.1016/0005-1098(83)90046-8)라는 짧은 논문을 썼다. 공장과 조종석이 자동화되면서 생긴 역설을 다룬 글이다. 자동화는 쉬운 일을 가져가고, 사람에게는 자동화가 처리하지 못하는 어려운 일만 남긴다. 그런데 쉬운 일을 하지 않게 된 사람은 감각을 잃는다. 결국 가장 어려운 순간에, 가장 연습이 덜 된 사람이 개입하게 된다.

AI 코딩도 같은 길 위에 있다. 평범한 CRUD, 익숙한 버그, 보일러플레이트는 AI가 가져간다. 사람에게 남는 건 AI가 헤매는 문제, 예를 들어 동시성 버그, 데이터 정합성, 장애 상황이다. 그런데 이런 문제를 푸는 감각은 평범한 코드를 수없이 짜고 읽으면서 길러진 것이다.

그래서 앞으로의 자세는 역설적이게도 **가끔은 일부러 직접 하는 것**이라고 생각한다. AI가 짠 코드를 그냥 넘기지 말고 읽는다. 이상하다고 느껴지면 왜 그런지 직접 재현해 본다. [SKIP LOCKED 글](../../backend/database/locking-reads.mdx)이 그렇게 나왔다. AI가 붙인 옵션 한 줄을 그냥 받아들이지 않고, MySQL을 띄워서 직접 돌려 봤기 때문에 쓸 수 있었던 글이다.

### 믿음 대신 검증을 설계한다

확률적인 도구를 믿는 방법은 하나다. 믿지 않아도 되게 만드는 것이다.

컴파일러는 환경을 고정하면 한 번 검증한 결과를 계속 믿을 수 있지만, AI의 출력은 매번 검증해야 한다. 그러니 사람이 눈으로 매번 확인하는 대신, **검증할 수 있는 형태로 일을 맡겨야** 한다. 테스트가 먼저 있으면 AI가 짠 코드가 맞는지 기계가 판정한다. 타입이 단단하면 엉뚱한 코드는 컴파일에서 걸린다. 작은 단위로 맡기면 리뷰할 수 있는 크기가 된다.

예전에 테스트와 타입은 "좋은 습관"이었다. AI와 일하는 시대에는 AI의 출력을 믿을 수 있게 만드는 핵심 장치가 된다. [사내 챗봇 설계](../sambot/sambot-design.mdx) 글에서 LLM에게 해석과 설명만 맡기고 조회·계산·판정은 코드에 남긴 것도 같은 생각이다.

물론 모든 일에 정답이 있는 건 아니다. 설계 대안을 펼쳐 보거나, 낯선 코드베이스를 훑거나, 아이디어를 내는 일은 애초에 검증할 정답이 없다. 이런 일은 오히려 AI에게 넓게 맡기기 좋다. 기준은 단순하다. **검증할 수 있는 일은 검증 장치와 함께 맡기고, 검증할 수 없는 일은 결정이 아니라 재료로만 받는다.** 최종 결정은 사람이 한다.

### 책임은 위임되지 않는다

1979년 IBM의 사내 교육 자료에는 이런 취지의 문장이 있었다고 한다. 컴퓨터는 책임을 질 수 없으므로, 관리상의 결정을 내려서는 안 된다.

AI가 짠 코드도 커밋하는 순간 내 코드다. 장애가 나면 "AI가 그렇게 짰어요"는 답이 되지 않는다. 일은 위임할 수 있어도 책임은 위임할 수 없다. AI가 더 많은 일을 할수록, 개발자의 일은 점점 **무엇에 내 이름을 걸 수 있는지 판단하는 일**에 가까워질 것이다.

### 무엇을 풀지 정하는 일

여기까지 쓰고 보니 한 가지가 빠져 있었다. 판단과 검증과 책임도 결국 **이미 정해진 문제**를 전제로 한다.

AI는 계속 발전할 것이다. 코드 작성뿐 아니라 테스트, 리뷰, 장애 분석까지 상당 부분을 맡길 수 있게 될 것이고, 검증 자체도 자동화의 대상이 될 수 있다. 그렇다면 개발자의 역할이 "AI가 만든 결과를 검수하는 사람"으로 줄어드는 걸까. 나는 오히려 반대라고 생각한다.

AI가 구현 비용을 낮출수록, **잘못된 문제를 열심히 푸는 비용**도 같이 낮아진다. 예전에는 만드는 데 몇 주가 걸려서 만들기 전에 한 번 더 고민했다. 이제는 하루 저녁이면 만들어지니, 고민 없이 만들어 버리기 쉽다. 토큰 대시보드도 하룻밤 만에 만들어졌지만, 정작 오래 고민한 건 "무엇을 재고 무엇을 재지 않을까"였다.

그래서 앞으로 더 중요해지는 건 문제를 발견하고 정의하는 능력이다. 운영팀이 매주 같은 질문을 Slack에 올린다는 걸 알아채는 것, 그게 검색의 문제인지 권한의 문제인지 구분하는 것, 무엇을 만들지 않을지 정하는 것. AI가 후보를 내 줄 수는 있어도, 이 판단까지 전적으로 맡기기는 어렵다.

### 말로 옮길 수 없는 것

철학자 마이클 폴라니는 『암묵적 영역(The Tacit Dimension)』(1966)에서 사람은 말할 수 있는 것보다 더 많이 안다고 했다. 이른바 [암묵지](https://en.wikipedia.org/wiki/Tacit_knowledge)다. 자전거 타는 법을 설명할 수 없어도 탈 수는 있는 것처럼, 지식의 상당 부분은 말로 옮겨지지 않는다.

AI에게 일을 맡기려면 필요한 맥락을 전달할 수 있는 형태로 옮겨야 한다. 프롬프트로, 문서로, 테스트로. 그 과정에서 우리는 자주 깨닫는다. 이 서비스가 왜 이렇게 생겼는지, 이 테이블에 왜 이 컬럼이 있는지, 운영팀이 실제로 어떻게 일하는지를 나도 제대로 말로 설명하지 못한다는 걸.

그래서 앞으로 개발자의 가치는 두 가지에 있다고 생각한다. 하나는 그 암묵지를 계속 쌓는 것, 다른 하나는 그걸 AI와 동료가 읽을 수 있는 형태로 꺼내 놓는 것이다. 이 스터디에서 글을 쓰는 이유도 결국 거기에 있다.

## 마치며

과거의 우리는 확률적인 도구를 어떻게 믿어야 할지 몰라 기웃거렸다. 지금의 우리는 매일 같이 일하고, 그 사용량은 가파르게 늘고 있다. 앞으로의 우리는 무엇을 풀지 정하고, 무엇을 맡기고, 무엇을 검증하고, 무엇에 이름을 걸지 아는 팀이 되어야 한다.

[사내 챗봇 설계](../sambot/sambot-design.mdx) 글과 이 글을 쓰면서 같은 생각에 두 번 닿았다. **AI에게 일을 맡기는 능력만큼, AI에게 맡기지 않을 일을 정하는 능력이 중요하다.**

토큰 대시보드는 그 과정을 비추는 거울 정도다. 거울에 비친 숫자보다 중요한 건, 그 숫자를 보며 우리가 어떤 질문을 던지느냐일 것이다. 한 달쯤 지나 월간 순위가 쌓이면, 숫자 너머로 우리가 AI를 대하는 방식이 실제로 바뀌었는지 다시 돌아보려고 한다.
